3. SEPARAR MODOS DE AÇÃO: SAC CONTÍNUO E DDQN DISCRETO
====================================================================

O ambiente precisa suportar:

    action_mode="continuous"   # SAC
    action_mode="discrete"     # DDQN

--------------------------------------------------------------------
3.1 Modo contínuo — SAC
--------------------------------------------------------------------

No modo SAC:

    action_space = spaces.Box(low=-1.0, high=1.0, shape=(3,), dtype=np.float32)

A ação bruta do agente deve ser convertida assim:

    raw_action -> softmax -> p_opt
    p_final = p_static + 0.5 * p_opt
    p_final = normalize(p_final)

Onde:

    weights = [0.3333, 0.4000, 0.2667]
    p_static = 0.5 * weights

Resultado final:
- eMBB recebe `p_final[0]`;
- URLLC recebe `p_final[1]`;
- MTC recebe `p_final[2]`.

Enviar para ns-3 em porcentagem ou fração conforme o parser C++ espera. Verificar o formato atual.

--------------------------------------------------------------------
3.2 Modo discreto — DDQN
--------------------------------------------------------------------

No modo DDQN:

    action_space = spaces.Discrete(len(ACTION_TABLE))

Criar tabela de ações discretas inspirada no artigo.

A tabela deve conter combinações:

    p0, p1, p2 ∈ {0.0, 0.1, ..., 1.0}
    p0 + p1 + p2 = 1.0

E, futuramente, scheduler:

    sch ∈ {0, 1, 2}
    0 = RR
    1 = PF
    2 = BCQI

Para três slices e resolução 0.1, a tabela com scheduler deve ter 198 ações, se seguir a formulação do artigo.

Criar módulo novo:

    ns-o-ran-gym/src/environments/rslaq_action_spaces.py

Com funções:

    build_discrete_action_table(step=0.1, include_scheduler=True)
    continuous_action_to_prb(raw_action, weights, static_fraction=0.5)
    discrete_action_to_prb(action_idx, action_table, weights, static_fraction=0.5)
    scheduler_id_to_name(scheduler_id)

Critérios de aceite:
- SAC envia ação contínua com shape `(3,)`.
- DDQN envia índice inteiro.
- O ambiente converte a ação corretamente.
- Não aplicar `softmax` duas vezes.
- Não passar matriz 3×3 para o ambiente DDQN.
- A ação final enviada para ns-3 sempre soma aproximadamente 1.0 ou 100%.

4. REFORMULAR OBSERVATION SPACE PARA O MODO DO ARTIGO
====================================================================

O artigo define o estado como matriz:

    s ∈ R^{4 × (J+1)}

Para 3 slices:

    shape = (4, 4)

Linhas:
    0: btx
    1: bfs
    2: rsh
    3: tdp

Colunas:
    0: eMBB
    1: URLLC
    2: MTC
    3: cell total

Tarefa:
Implementar dois modos de observação:

    observation_mode="paper"
    observation_mode="debug"

O modo `paper` deve retornar:

    np.ndarray shape=(4,4), dtype=np.float32

O modo `debug` pode manter o formato antigo, se útil para compatibilidade.

Criar módulo:

    ns-o-ran-gym/src/environments/rslaq_kpis.py

Responsável por:
- ler KPIs vindos do ns-3;
- normalizar métricas;
- construir estado `4x4`;
- calcular coluna `cell total`;
- lidar com valores ausentes.

Mapeamento sugerido:
- `btx`: bytes transmitidos/oferecidos ou bytes TX no intervalo;
- `bfs`: buffer status ou proxy de backlog/perda/queue, conforme disponível;
- `rsh`: resource share ou allocated PRB/RBG share;
- `tdp`: dropped/transmitted dropped bytes ou perda efetiva.

Se alguma métrica real ainda não existir no ns-3:
- usar proxy temporário;
- documentar claramente;
- adicionar TODO;
- não mascarar como se fosse métrica exata do artigo.

Normalização:
- throughput/bytes devem ser normalizados por capacidade ou máximo observado/configurado;
- `rsh` deve estar em [0,1];
- perdas/buffer devem ser limitadas/clampadas para evitar explosão numérica.

Critérios de aceite:
- `env.observation_space` bate com o estado retornado.
- `reset()` retorna `obs` com shape correto.
- `step()` retorna `obs` com shape correto.
- O estado inclui coluna da célula.
- O relatório documenta quais métricas são reais e quais são proxies.

5. IMPLEMENTAR REWARD SLA-AWARE DO RSLAQ
====================================================================

Criar módulo:

    ns-o-ran-gym/src/environments/rslaq_reward.py

A reward deve ser configurável por cenário.

Cenários:
- low_traffic
- normal
- congestion
- stressed
- insufficient_resources

Configuração base:

    weights = [0.3333, 0.4000, 0.2667]

SLAs aproximados:
- low_traffic:
    eMBB min throughput = 10 Mbps
    eMBB soft max throughput = 15 Mbps
    URLLC max bfs/loss/buffer = 3%
- normal:
    eMBB min throughput = 10 Mbps
    eMBB soft max throughput = 15 Mbps
    URLLC max bfs/loss/buffer = 3%
- congestion:
    eMBB min throughput = 10 Mbps
    eMBB soft max throughput = 15 Mbps
    URLLC max bfs/loss/buffer = 3%
- stressed:
    eMBB min throughput = 20 Mbps
    eMBB soft max throughput = 25 Mbps
    URLLC max bfs/loss/buffer = 3%
- insufficient_resources:
    eMBB min throughput = 20 Mbps
    eMBB soft max throughput = 25 Mbps
    URLLC max bfs/loss/buffer = 3%

Implementar:

    SLA_BY_SCENARIO = {...}

Reward conceitual:
- Se outage SLA crítico ocorrer:
    reward = -sum(weights das slices violadas)
    terminated = True ou opcionalmente `outage=True` sem terminar, configurável.
- Se soft KPI for violado:
    reward = 0 ou penalidade configurável.
- Caso contrário:
    reward = weighted optimization reward + scheduler_cost_term.

Para resource-only, scheduler_cost pode ser 1.0.
Quando scheduler_id estiver ativo:
    RR -> cost 1
    PF/BCQI -> cost 2

Métricas mínimas:
- eMBB: throughput por slice.
- URLLC: buffer/loss/delay proxy.
- MTC: throughput ou entrega efetiva.

Implementar função:

    compute_rslaq_reward(metrics, scenario, action_info=None, config=None) -> RewardResult

Onde `RewardResult` pode ser dataclass contendo:
- reward
- terminated
- outage_flags
- soft_flags
- optimization_terms
- debug_info

Critérios de aceite:
- Reward não depende de variáveis globais implícitas.
- Reward registra no `info` quais SLAs foram violados.
- Reward usa `effective_lost`/`effective_pdr`, não `FlowMonitor lost_packets`.
- Reward é testável com métricas sintéticas.
