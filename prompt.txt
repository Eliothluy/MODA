Atue como um engenheiro sênior de ns-3/5G-LENA, especialista em 5G NR MAC scheduling, OFDMA scheduling, QoS flows, RLC/MAC, tracing, CMake do ns-3 e simulações reprodutíveis.

Contexto do projeto:
Tenho uma simulação 5G-LENA network-only inspirada no artigo RSLAQ. A versão atual usa:
- 1 gNB
- 20 UEs
- 3 slices: eMBB, URLLC e MTC
- 5 UEs eMBB
- 5 UEs URLLC
- 10 UEs MTC
- 2.59 GHz
- 10 MHz
- numerologia 0 / SCS 15 kHz
- TDD
- 50 PRBs aproximados
- tráfego UDP downlink
- cenários: low, normal, congestion, stressed, insufficient
- scheduler atual funcional: `ns3::NrMacSchedulerOfdmaQos`
- slicing atual aproximado: BWP-per-slice + QoS-flow routing

O problema:
A abordagem atual funciona como baseline network-only, mas ainda não é um scheduler MAC slice-aware real. Os PRBs usados por slice não são medidos a partir do MAC, e o `prb-allocation.csv` atual contém orçamento aproximado, não medição real. Quero implementar o scheduler real descrito na análise: um scheduler OFDMA QoS + slice-aware, com quota de recursos por slice, medição real de RBG/PRB por slice e uso de um único BWP compartilhado.

Objetivo principal:
Implementar um scheduler MAC slice-aware real no 5G-LENA, baseado no `NrMacSchedulerOfdmaQos`, que controle e registre recursos por slice dentro de um único pool OFDMA.

Crie uma nova classe:
- `NrMacSchedulerOfdmaSliceQos`

Arquivos esperados:
- `ns-3-dev/contrib/nr/model/nr-mac-scheduler-ofdma-slice-qos.h`
- `ns-3-dev/contrib/nr/model/nr-mac-scheduler-ofdma-slice-qos.cc`

Não modifique diretamente `NrMacSchedulerOfdmaQos`, exceto se for inevitável. Prefira herança ou extensão limpa.

A nova classe deve usar como base:
- `NrMacSchedulerOfdmaQos`

Motivo:
O `NrMacSchedulerOfdmaQos` já funciona com QoS flows e foi validado no cenário atual. A nova classe deve preservar a lógica QoS existente, mas adicionar consciência de slice, quota de recursos, medição real e controle por slice.

Tarefa 8 — Implementar soft slice-aware scheduling:
Depois da versão measurement-only, implemente priorização soft por slice.

Sobrescreva GetUeCompareDlFn() e, se possível, GetUeCompareUlFn().

A ordenação deve considerar:

déficit do slice em relação ao orçamento;
lógica QoS original do NrMacSchedulerOfdmaQos.

Exemplo conceitual:

double GetSliceDebt(uint8_t sliceId) const
{
    double budget = m_dlBudgetRbgThisFrame.at(sliceId);
    double used = m_dlUsedRbgThisFrame.at(sliceId);

    if (budget <= 0.0)
    {
        return -1.0;
    }

    return (budget - used) / budget;
}

Comparador:

se dois UEs pertencem a slices diferentes, priorizar o slice com maior déficit;
se pertencem ao mesmo slice, usar a comparação QoS original:
NrMacSchedulerUeInfoQos::CompareUeWeightsDl(...)
ou função equivalente real da API local.

Não quebre a lógica QoS existente. O scheduler deve continuar funcionando com QoS flows.
